## 1. 项目概述

### 1.1 简介

危信是一款桌面端微信「危险言语」提前拦截工具，开源免费。在用户按下发送键（Enter / Ctrl+Enter）之前，对当前聊天窗口上下文与待发送消息进行识别与语义分析，判断「消息内容」与「当前聊天场景」是否匹配；若不匹配（存在误发风险），在操作系统层面阻断发送按键并弹出提示对话框。

### 1.2 问题场景

日常工作中有正式的工作群、客户群、公司群，同时也有好友、家人等私聊。用户在与好友吐槽、抱怨时被工作打断，回复完工作消息后若忘记切换回朋友聊天窗口，继续输入吐槽内容并发送，短时间未察觉可能造成严重后果；即便快速撤回，也无法确定是否已被人看到。

### 1.3 产品目标

1. 在发送动作发生**之前**完成拦截判定，而非事后补救。
2. 全流程**用户无感知**：不占用过多系统资源，不影响正常键盘输入与其他软件使用。
3. **合规安全**：只通过操作系统公开能力（全局键盘事件、屏幕截图）工作，严禁触碰目标程序（微信）的文件、内存、进程、网络协议与内部数据。
4. **可扩展**：目标程序、区域标签、违禁词库、语义模型全部配置化/插件化，后续可适配微信之外的聊天软件。

### 1.4 名词约定

| 名词 | 含义 |
|---|---|
| 目标程序 | 被守护的聊天软件进程，v1.0 默认微信（WeChat.exe），通过配置可切换 |
| 守护状态 | 危信正在对目标程序执行「预分析 + 按键裁决」的工作状态 |
| 危险消息 | 经判定与当前聊天场景不匹配、不建议发送的消息 |
| 预分析 | 在按键发生前，后台低频执行的「截图→区域→OCR→语义」流水线 |
| 裁决 | 捕获到发送按键时，基于预分析结果做出的放行/阻断决定 |

## 3. 合规红线（最高优先级约束）

以下约束为**不可协商项**，任何模块设计、实现、测试均不得违反；违反即视为缺陷，必须修复后方可发布：

| 编号 | 红线 |
|---|---|
| C-01 | 严禁读取、修改、扫描微信（或任何目标程序）的安装目录、数据文件、数据库 |
| C-02 | 严禁对目标程序进程进行注入、Hook（API Hook / DLL 注入）、内存读写、窗口子类化 |
| C-03 | 严禁逆向、调用目标程序的网络协议或内部接口 |
| C-04 | 严禁检测、扫描目标程序进程内部状态以「对抗」其安全机制 |
| C-05 | 允许且仅允许使用：操作系统级全局键盘事件（WH_KEYBOARD_LL 等公开机制）、前台窗口查询（GetForegroundWindow 等公开 API）、屏幕截图（对屏幕像素，而非对目标程序内部） |
| C-06 | 判定目标程序是否前台激活，仅用于决定危信自身「挂起/唤醒」，不向目标程序发送任何事件 |
| C-07 | 所有识别数据（截图、OCR 文本、消息内容）仅留存于本机，默认不外发；debug 图片日志写入本地日志目录，可由用户一键清空 |
| C-08 | 严禁向目标程序注入任何按键、点击或窗口消息（SendInput / keybd_event / mouse_event / PostMessage / SendMessage 目标为目标程序一律禁止）；「仍然发送」仅通过内部 allow-once 标志放行用户自己的下一次按键，**不代发**（详见合规文档红线 3「只减不加」） |

> 合规验证方式见《开发设计文档》§11.3 与《合规与风险说明》§6。发布前必须逐项自查 C-01 ~ C-08。

## 4. 功能需求

> 编号规则：FR-<模块>-<序号>。优先级：P0 必须 / P1 重要 / P2 增强。

### 4.1 消息源模块（拦截输入）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-SRC-01 | 注册系统级低级键盘钩子，监听全局 Enter、Ctrl+Enter 按键 | P0 |
| FR-SRC-02 | 钩子回调内**禁止**任何重计算；仅查询最近一次预分析的缓存判定结果，单次钩子处理耗时 < 5ms | P0 |
| FR-SRC-03 | 判定为危险时吞掉该次按键（不向目标程序传递），并通知前端弹窗；判定为安全或无缓存结果时原样放行 | P0 |
| FR-SRC-04 | 挂起算法：目标程序未处于前台激活状态时，危信进入挂起态——钩子放行一切按键、预分析停止、**推理模型默认卸载**（NFR-04 内存分级）；目标程序回到前台后自动唤醒并按需重载模型 | P0 |
| FR-SRC-05 | 前台检测仅使用公开 API 判断前台窗口所属进程是否为配置的目标进程名，不做任何进程内部探测（合规 C-05/C-06） | P0 |
| FR-SRC-06 | 发送快捷键可配置（Enter / Ctrl+Enter 二选一，与微信「发送消息」设置对应） | P1 |
| FR-SRC-07 | 提供「暂停守护」开关（快捷键 + 托盘菜单），暂停后行为等同于未安装本软件 | P1 |
| FR-SRC-08 | 模块接口预留鼠标事件源（点击发送按钮），v1.0 不实现 | P2 |
| FR-SRC-09 | 输入法组合状态（拼音候选等）期间，任何按键一律放行，绝不吞掉输入法按键；组合提交（含回车选字）视为内容修改使草稿纪元 +1。IME 状态仅经公开系统事件（`EVENT_OBJECT_IME_*`）获取，不接触目标程序 | P0 |

### 4.2 截图模块

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-CAP-01 | 通过屏幕 DC 仅拷贝目标窗口矩形区域（仍是屏幕像素，合规 C-05；不做窗口定向捕获），单次截图耗时不高于 50ms（1080p 窗口基准） | P0 |
| FR-CAP-02 | 通过公开 API 获取目标程序窗口的坐标与大小，从屏幕截图中裁剪出目标窗口区域，得到原始图片 | P0 |
| FR-CAP-03 | 目标窗口最小化或不在前台时，返回明确的「不可用」状态而非错误图片（Guard 仅在前台激活时工作，前台窗口不存在整体遮挡；置顶窗口局部遮挡属可接受边角，走 fail-open） | P0 |
| FR-CAP-04 | 多显示器、DPI 缩放（125%/150% 等）下坐标换算正确 | P0 |
| FR-CAP-05 | 原始图片与裁剪图片可按配置写入 debug 日志目录（默认关闭） | P1 |

### 4.3 区域划分模块

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-ROI-01 | 基于 YOLO 目标检测模型，对窗口截图识别可配置的区域标签（tag），v1.0 内置标签：`chat_list`（聊天列表）、`chat_window`（聊天窗口）、`chat_target`（当前聊天对象）、`msg_input`（消息输入框） | P0 |
| FR-ROI-02 | 输出每个标签对应的边界框（x, y, w, h）与置信度；未检出某标签时返回空结果而非异常 | P0 |
| FR-ROI-03 | 标签集合通过配置定义（名称、颜色、启用状态），新增标签无需改代码，只需替换模型与配置 | P0 |
| FR-ROI-04 | 支持用户用 dc_uitag 标注 10~20 张图片自行训练并导入自定义模型；发布版内置一套微信的预训练模型 | P0 |
| FR-ROI-05 | 单次推理耗时：CPU ≤ 300ms，GPU ≤ 80ms（1080p 窗口图基准） | P0 |
| FR-ROI-06 | 检出结果图片（带框叠加）可写入 debug 日志目录 | P1 |

### 4.4 文字识别模块（OCR）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-OCR-01 | 对区域划分结果中的指定区域（默认 `chat_target`、`msg_input`）进行 OCR，输出文字内容与文本框坐标 | P0 |
| FR-OCR-02 | 采用 RapidOCR / PaddleOCR ONNX 模型，中文识别准确率满足：常规聊天文字场景字段级准确率 ≥ 95%（验收集见设计文档 §10） | P0 |
| FR-OCR-03 | 单次识别耗时：`msg_input` 区域 CPU ≤ 200ms / GPU ≤ 50ms | P0 |
| FR-OCR-04 | 支持对划分结果先做一次轻量图像整理（缩放、灰度等）以提升识别率，整理策略可配置 | P1 |
| FR-OCR-05 | 识别文本与可视化结果可写入 debug 日志目录 | P1 |

### 4.5 文本识别模块（语义/危险判定）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-SEM-01 | 分层判定：L1 规则引擎（违禁词、正则、场景-词表匹配，毫秒级）→ L2 本地语义模型（场景-消息匹配度/危险度评分，ONNX） | P0 |
| FR-SEM-02 | 输入：当前聊天对象名称（来自 OCR `chat_target`）、输入框消息文本（来自 OCR `msg_input`）、可选的聊天窗口上下文摘要；输出：危险概率/权重、命中原因（规则命中项或模型分数）、建议（放行/警告/阻断） | P0 |
| FR-SEM-03 | 支持「聊天对象画像」配置：用户可将聊天对象标记为「正式」（工作群/客户/领导）或「随意」（好友/家人），判定逻辑据此调整阈值；未标记对象按「正式」保守处理 | P0 |
| FR-SEM-04 | 违禁词库为用户可编辑的配置文件（词条、严重级别、适用场景），支持热重载 | P0 |
| FR-SEM-05 | L2 语义模型采用 **int8 量化** ONNX 模型（bge-small-zh 级别候选，M3 spike 实测定稿），常驻内存约 25MB，支持 GPU 加速，无 GPU 时 CPU 运行且单次评分 ≤ 200ms | P1 |
| FR-SEM-06 | 判定结果附带可读理由（如「命中违禁词：xx」「与正式场景语义不匹配，置信度 0.87」），供前端展示 | P0 |
| FR-SEM-07 | 提供「本次不再提示」「将此对象标记为随意」等快捷处理入口所需的判定上下文 | P1 |

### 4.6 前后端通信与阻断提示模块

## 5. 非功能需求

| 编号 | 类别 | 需求 |
|---|---|---|
| NFR-01 | 性能-感知 | 正常打字（非发送键）零感知：钩子处理 < 5ms，预分析在后台低频执行且不阻塞输入 |
| NFR-02 | 性能-裁决 | **发送路径零等待**：发送键按下到裁决完成仅读取缓存结果，p99 < 10ms；**任何情况下不得在按键路径上等待分析计算**，分析耗时与按键延迟完全解耦，杜绝「发送后卡在分析」的 > 200ms 可感知场景；无有效缓存时按 fail-open 放行（详见开发文档 §2） |
| NFR-03 | 性能-流水线 | 预分析分双速执行：快环（输入变化触发，仅输入框 OCR + 重判）≤ 200ms（CPU）/ ≤ 100ms（GPU）；慢环（全链路：截图→裁剪→区域→OCR→语义）≤ 2s（CPU）/ ≤ 800ms（GPU）；两者均在后台线程执行，不占用按键与 UI 线程 |
| NFR-04 | 资源（按进程分级） | 后端进程（Rust）私有工作集：**挂起态 ≤ 25MB、守护态 ≤ 80MB**（含全部 int8 模型常驻与截图缓冲）；推理线程低于正常优先级，守护态空闲 CPU 均值 ≤ 3%。WebView2 进程内存单独核算、不计入后端预算（常态仅预建拦截提示弹窗一个实例，设置主窗口关闭即销毁其 WebView）——Tauri 架构下「总内存 10-20MB」物理不可达，已确认按后端进程口径考核（设计文档 §12.1） |
| NFR-05 | GPU | 有可用 GPU 时推理自动加速；GPU 占用为短时突发，不常驻占满；用户可强制指定 CPU |
| NFR-06 | 隐私 | 所有数据不出本机；图片日志默认关闭；提供一键清空 |
| NFR-07 | 稳定性 | 守护进程连续运行 24h 无内存泄漏（增长 < 10%）；任一模块推理失败降级为「放行 + 记录日志」，不得导致按键丢失或系统卡键 |
| NFR-08 | 可扩展 | 目标程序、区域标签、违禁词库、聊天对象画像、模型文件全部可配置/可替换 |
| NFR-09 | 兼容性 | Windows 10 (1809+) / 11；微信 PC 版主流版本（内置模型针对当前主流版本训练，版本差异通过用户自训练兜底） |
| NFR-10 | 可观测 | 每次拦截/放行均有结构化日志（时间、模块耗时、判定结果、原因），可供排障 |
| NFR-11 | 体积 | 安装包 ≤ 60MB（含全部内置模型：YOLO11n ~6MB、RapidOCR ~15MB、int8 语义模型 ~25MB） |

## 6. 用户故事（关键路径）

1. **误发拦截**：用户在好友窗口输入吐槽内容 → 被工作消息打断切换到公司群 → 继续输入并按 Enter → 危信检测到「当前对象为正式场景，消息语义不匹配」→ 吞掉 Enter → 弹窗提示 → 用户点击「取消发送」→ 消息未发出。
2. **确认放行**：同上场景，用户确认消息确实要发 → 点击「仍然发送」→ 危信放行下一次发送键并关闭弹窗 → 用户再按一次 Enter → 消息正常发出（危信不代发任何按键，红线 C-08）。
3. **无感日常使用**：用户在微信正常聊天，消息与场景匹配 → 全程无弹窗、无卡顿。
4. **非微信时段**：用户切到浏览器/IDE 工作 → 危信自动挂起，资源占用趋近于零。
5. **自助训练**：用户微信版本界面差异大导致区域识别不准 → 用 dc_uitag 标注 15 张截图 → 导出训练集训练 → 在设置中导入自定义模型 → 恢复准确识别。
