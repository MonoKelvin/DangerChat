## 结论

Gate 0 尚未通过。本轮把此前依赖人工操作的三项改为自动验证并取得数据，
四项门槛在**自有合成环境**下全部达标；仍缺的是真实微信界面与多显示环境的证据。

| 门槛 | 自动验证结果 | 仍缺的证据 |
|---|---|---|
| M0-A 键盘守卫 | PASS：49 项测试 + 20 万事件基准，p99 0.1 µs | 物理按键投递耗时（可选交叉验证） |
| M0-B 输入法 | PASS：IMM32 四场景判定正确 | 真实输入法候选行为；组合态未真正构造 |
| M0-C 捕获/定位/OCR | PASS：定位 8/8、标题 1.000、CER 0.0000 | **真实微信界面与独立标注集** |
| M0-D 端到端延迟 | PASS：反馈最大 13 ms、提示 p95 436 ms | 真实界面下复测 |

**为什么仍判定 Gate 0 未通过**：`docs/01` §16 要求算法结论来自独立、
按组切分的标注集。当前全部 OCR 与定位数据来自 8 个合成场景，
使用固定字体与固定文案，不能代表真实微信的字体渲染、缩放与布局变体。
这一项无法靠本机自动化补齐，需要授权采集真实界面截图。

在该证据补齐之前不创建 M1/M2 工程骨架。

### 已通过：回调处理耗时

`m0 hook-bench 200000`，20 万条混合事件（字母、修饰键、发送键各路径）：

| 指标 | 实测 | 门槛 | 结果 |
|---|---|---|---|
| p50 | 0.000 µs | — | 低于计时器分辨率 |
| p95 | 0.100 µs | — | — |
| p99 | 0.100 µs | ≤ 250 µs | PASS |
| 最大 | 6.900 µs | ≤ 2000 µs | PASS |

测量方式：事件直接送入 `process_event`，即真实回调内实际执行的那段代码，
不调用 `SendInput` 等任何输入合成 API，因此红线扫描保持零白名单。

**测量精度说明**：QPC 分辨率为 100 ns，单次调用快于该精度，
故 p50 显示 0 µs 表示「低于计时器可分辨的下限」，不是零耗时。
门槛判定依据 p99 与最大值，二者远高于分辨率，结论不受影响。

**未计入**：操作系统把按键投递到回调的传输耗时。该段不属于本进程可控范围，
如需交叉验证可运行 `m0 hook-latency 30` 并配合真实打字。

## M0-B 输入法

### 已通过：IMM32 判定自动验证

`m0 ime-verify`，在自有窗口上程序化构造 IMM32 状态：

| 场景 | 判定 | 让给输入法 | 结果 |
|---|---|---|---|
| 输入法关闭（英文直接输入） | `NotComposing` | 否 | PASS |
| 输入法打开、无组合串 | `Unknown` | 是 | PASS |
| 写入组合串 | `Unknown` | 是 | PASS（见下） |
| 窗口无输入法上下文 | `Unknown` | 是 | PASS |

实现要点：

- `Unknown` 与 `Composing` 都映射为「让给输入法」，这是安全默认值；
- 状态由协调线程周期采样后经命令队列发布给守卫，
  **钩子回调只读取已发布的布尔值**，不在快路径调用 IMM32。

**一项未真正验证到的场景**：写入组合串时 `ImmSetCompositionStringW` 返回成功，
但组合串读不回来——该 API 只对拥有输入法焦点的上下文生效。
因此「存在组合串时判为 `Composing`」这条路径**尚未被真实构造出的组合态覆盖**。
该场景当前退化为「打开无组合串」，判定仍落在安全侧，验证工具会显式打印这一事实，
不用 PASS 掩盖。

### 仍需人工抽查

真实输入法的候选行为差异（微软拼音、五笔、emoji 面板、Enter 换行、
快捷键反向配置）建议用 `m0 ime-hook-probe 30` 抽查。
若某输入法走 TSF 而不更新 IMM32 组合串，探测返回 `Unknown`，
而 `Unknown` 已映射为透传，属于安全侧失败。

### 已通过：区域定位（合成）

`m0 layout-eval`，自有合成测试窗口，8 个场景（4 种窗口尺寸 × 浅/深主题），
连续 4 次运行均为 8/8：

| 指标 | 实测 | 结果 |
|---|---|---|
| 关键 ROI 达标场景 | 8 / 8 | PASS |
| 最低 IoU（聊天标题） | 0.981 | PASS |
| 最低 IoU（消息上下文） | 0.996 | PASS |
| 最低 IoU（输入框） | 0.991 | PASS |
| 定位耗时平均 | 1.8 ms | — |

定位只使用灰度、边缘梯度与行列一致性，不依赖文字内容，也不使用目标检测模型。
结构签名由几何比例构成，不含任何文本。

**本轮修正的两个缺陷**：

1. 三个 Harness 此前用 `foreground_snapshot()` 取窗口，会在终端抢占焦点时
   捕获到错误窗口。改为按已知 HWND 读取快照并校验可见性。
2. 捕获前只用固定 `sleep` 等待绘制，导致 GDI 屏幕级捕获读到半绘制帧，
   定位随机失败（`NoSidebarBoundary`/`NoComposeSeparator` 在不同运行中命中不同场景）。
   改为等待 `WM_PAINT` 计数增长后再捕获；超时按失败处理，不重试掩盖。

此前记录的"DWM 扩展边界导致标题栏被误判"已修正为按客户区
（`GetClientRect` + `ClientToScreen`）裁剪。

## M0-D 端到端延迟

### 合成分析链达标，但**门槛未通过**

`m0 e2e-latency 30`（前 5 轮预热不计入），三次运行：

| 运行 | p50 | p95 | p99 |
|---|---|---|---|
| 1 | 692.8 ms | 799.1 ms | 829.4 ms |
| 2 | 633.5 ms | 673.5 ms | 678.4 ms |
| 3 | 634.2 ms | 718.2 ms | 758.3 ms |

链路覆盖：显示器捕获 → 结构定位 → 内存 PNG 编码 → 保活 OCR 子进程 → 固定规则决策。

**为什么不能判定 M0-D 通过**：

- 不含物理按键、钩子回调、协调线程排队；
- 不含风险提示 UI 的渲染与呈现；
- p95 最差一次为 799.1 ms，距 800 ms 门槛不足 1%，
  任何额外阶段都极可能使其超标。

### 完整链路已通过（合成窗口）

`m0 full-latency 30` 串联全链路，不省略 UI 渲染：

```
守卫判定抑制发送键（t0）
  → 「正在检查」提示绘制完成
  → 捕获 → 结构定位 → OCR → 固定规则决策
  → 结果提示绘制完成（t1）
```

三次运行：

| 运行 | 反馈 p50 | 反馈最大 | 提示 p50 | 提示 p95 |
|---|---|---|---|---|
| 1 | 1.6 ms | 13.0 ms | 338.6 ms | 436.1 ms |
| 2 | 1.5 ms | 3.0 ms | 335.2 ms | 397.1 ms |
| 3 | 1.6 ms | 3.0 ms | 338.1 ms | 405.6 ms |

| 门槛 | 判定口径 | 结果 |
|---|---|---|
| 「正在检查」≤ 100 ms | 全部样本最大值 | PASS（最差 13.0 ms） |
| 结果提示可见 p95 ≤ 800 ms | 分位数 | PASS（最差 436.1 ms） |
| 样本量 ≥ 20 | — | PASS（30） |

反馈门槛按**最大值**而非分位数判定：100 ms 是对每次事务的承诺，
偶发超时同样会让用户看到无响应的界面。

实现要点：

- t1 取自提示窗 `WM_PAINT` 的 `EndPaint` 返回后，代表像素已提交，
  **不用「请求显示」的时刻冒充「已可见」**；
- 提示窗使用 `WS_EX_NOACTIVATE`，永不抢焦点，按键始终发往原目标窗口；
- 事件直接送入领域层 `GuardCore`，不调用任何输入合成 API；
- 该设施不签发许可，因此不存在放行路径。

**未计入**：操作系统投递按键到钩子回调的耗时（微秒量级，由 `hook-bench`
与 `hook-latency` 单独覆盖）。真实微信界面下的表现仍未测。

### OCR 检测分辨率标定

初次测量 p95 为 1656.7 ms（FAIL）。定位后确认瓶颈完全在 OCR：
捕获 + 定位约 20 ms，OCR 单次约 1.6 s（标题 693 ms + 草稿 919 ms）。

在合成集上比较文本检测长边上限：

| `det_limit_side_len` | 标题精确匹配 | 草稿语料 CER | 单次 p50 |
|---|---|---|---|
| 736（默认） | 1.000 | 0.0000 | 997 ms |
| 480（当前） | 1.000 | 0.0000 | 399 ms |
| 320 | 1.000 | 0.0000 | 167 ms |

三档精度相同。选择 480 而非最快的 320，是为对更小字号保留分辨率余量。
该参数只影响检测阶段分辨率，不改变识别模型；
**真实界面字号与之不同时必须重新标定**。
